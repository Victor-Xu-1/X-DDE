# 持续维护流程

[质量规范入口](README.md) · [验证分层](validation.md) · [证据清单](evidence.md)

## 1. 先确认问题，再实现修复

优先级依次为：数据与科学结果正确性、资源与安全边界、可靠性、操作和执行反馈、视觉与可访问性、纯整理。先把可观察的问题及其影响说清楚；不为满足 PR 数量制造问题或拆散一个不可独立验收的修复。

1. 查现有 Issue、PR、远端分支和活动工作，按「模块 + 症状 + 根因」去重。已有负责人或 PR 时续接原记录，不重新开工。
2. 已证实的问题先建立或补全 Issue，记录影响、复现条件、实际与预期结果、来源/版本、证据、初步根因和可判断的验收条件。未确认的现象标记为待调查，不能包装成确定缺陷。
3. 在 Issue 中明确唯一实现负责人、文件及接口/数据写入边界、直接消费者、隔离工作目录/分支、base SHA、验证层级和预期检查。与其他工作交叉时，先协商所有权再编辑。
4. PR 关联 Issue，使用 `Refs #编号` 等普通引用。不要用 `Closes`、`Fixes`、`Resolves` 等自动关闭语法，让合并先于合并后验证关闭问题。
5. 合并后确认目标行为、版本及相关 main CI，再由负责人附证据关闭 Issue。保留未完成验收、回归和剩余范围；有阻塞时 Issue 继续开放。

安全问题先通过仓库所有者认可的私密渠道协调，公开 Issue/PR 只保留适当的影响摘要；不得公开利用步骤、凭据、私有研究材料或可直接利用的细节。公开范围不明确时先确认。

## 2. 并行上限与唯一所有者

一次最多六项活跃工作，默认三个互不重叠的实现任务，保留一个独立审查、一个 CI/整合和一个弹性名额。六项是工作上限，不是应填满的目标，也不表示任何服务的计算配额。维护负责人分配任务；存在待审候选时优先保留审查能力。

- 每项实现使用独立分支、工作目录和可变环境；只读下载缓存可共享，运行状态、数据库、构建输出不能互相覆盖。
- 所有权按模块、协议、数据写入和消费者划分，不能只看文件名。共享接口、版本镜像、安装流程或同一分支的写入先串行协调。
- 交接前查看原任务状态、未提交差异、远端 head 和在途 CI，保存有效工作并确认旧负责人停止写入。静默或计时超限本身不是停止证明。
- 一个任务只有一个当前写入者。人工登记不是自动互斥机制；目录消失或工作恢复后，以远端 Issue、分支、PR、CI 重新核实状态。

问题记录应能找到负责人、阶段、base/head SHA、最后核实时间、下一步、PR/CI 链接和阻塞/恢复条件；可引用现有 Issue/PR 元数据，不要求重复抄写。小问题用 3–5 个字段说清影响、复现、范围/负责人、验收和关联记录即可。使用可区分的阶段：待复现、已认领、修复中、待独立审查、待 CI、CI 失败待修、待整合、刷新基线中、已合并待确认、完成；等待授权、环境不可用和暂缓需明确标注，不能写成成功。

## 3. 候选 PR 的最低证据

按风险采用最短充分路径，不把每个 PR 变成全项目审计：

- 文档、文本和无行为影响的小样式改动：聚焦链接/格式/静态检查，加一名独立审查人；实际可见外观改变时检查受影响画面即可，不运行全部模块。
- 交互改动：受影响流程、直接消费者和主要失败/恢复路径的定向回归及真实浏览器检查。
- 并发、数据身份、迁移、资源边界和科学语义改动：补足相应竞态、失败、兼容性及真实科学证据，不用轻量等级降低风险门槛。

每个 PR 选择不超过七个适用验收项；复杂问题可链接专项证据，但不机械复制全套清单。所有既有适用 CI 必须成功，轻量流程不授权跳过它们。

- 尽可能先用相同范围证明原基线失败、修复后通过；无法前后对照时说明限制。
- 覆盖改变的模块及直接消费者。并发、锁、超时、截断、取消、资源上限、异常清理等修复必须覆盖对应失败路径。
- 记录命令、环境、输入、执行结果、base/head SHA 和预期 CI。局部通过不能表述为全项目通过；从未运行、受阻和失败分别记录。
- 检查差异、格式、无关文件、依赖和锁文件变化；保留原始数据、历史版本和未完成工作。
- 至少一名非作者完成独立审查，核对根因、实现、回归可信度、接口/数据兼容、资源边界、CI 范围、回退方案及适用的真实浏览器证据。关闭全部阻塞发现。
- 发布后核对远端 head 和树与审查对象一致。head/base 变化先撤销就绪状态；重新验证新树，非平凡功能变化重新独立审查。仅版本/基线变化也必须记录审查确认及其检查范围。

同一精确 SHA/树、输入、环境和执行范围的有效证据可引用复用，不重复跑相同检查或安排多轮相同全文审查。整合负责人检查审查结论、base/head、差异、CI 和新增风险；只有实质变化或证据失效才扩大重审。功能树相同不免除新 head 的 CI 核验，base 变化也不允许复用旧合成合并提交的 CI 结论。

未完成的候选保持草稿。文档声明、截图生成、代码审查或测试数量不能替代缺少的必要验收。

## 4. 精确提交的 CI 门槛

有效 PR 必须同时满足：最终 head 的全部适用 CI 实际成功、至少一次独立审查无阻塞、所有必要的浏览器/科学验收完成。只有有效 PR 才计入整合数量。

草稿创建数、旧 head 的绿灯、正在排队/运行、失败、取消、缺检查或必要 job 被跳过均不计数。仅当审查过触发条件、确认某可选 job 不适用并记录理由时，才接受该项跳过；失败后依赖 job 被跳过不属于不适用。

1. 从改变的文件和直接消费者列出工作流、事件、模式及所需 job，不只看 PR 页面的绿灯。
2. 查询所有相关 `push`、`pull_request` 和获准的 `workflow_dispatch`，处理分页，按 SHA、工作流、事件和执行次数核对最新适用结果。
3. PR 合成合并提交的检查记录实际执行 SHA 及对应 base/head；不能误写为直接执行 head，或在 base 改变后继续使用旧合成提交证据。
4. 版本调整、路径过滤或基线刷新导致门禁未触发时，重新确认检查范围。在已有授权内使用有限且明确的现有派发入口，核对 ref 派发前后及实际 run 的 SHA；不以补 CI 为名启动额外科学任务或全套检查。
5. 唯一路径超出授权时保留阻塞并请求决定，或另提审查过的最小 CI 修复。不得移除检查、放宽断言、恢复旧预期或隐藏失败。

CI 失败先看具体日志，用相同范围区分新回归、基线失败与基础设施问题。只有已证实的偶发基础设施失败才原样重试一次；再次失败进入诊断，不连续 rerun 碰运气。

## 5. 合格即审，逐项串行整合

每项候选必须有可说明并验证的实质收益，并按问题、根因和已有改动去重；不制造或重复修改来增加 PR 数量。CI 完成后及时审查，最终 head 的全部适用 CI、必要验收和独立审查通过即进入串行整合，不等待候选数量或每日批次。优先完成已合格候选，再扩大新修复范围；存在真实依赖、资源或授权阻塞时明确说明原因。多个独立 main 更新仍不能共用一个发布编号。

整合负责人一次只处理一个候选，其他作者不得同时更新 main 或竞争修改其候选版本：

1. 读取实时 main 完整 SHA、候选 head、冲突/审查/授权状态，确认没有另一项在途整合。
2. 必要时刷新候选基线，正确处理候选内已有版本提交，不能在过期候选版本上盲目再 bump。
3. 依照 [AGENTS.md](../../AGENTS.md) 的版本规则，以当时 main 为准，由候选唯一所有者运行 `uv run --locked python scripts/release-version.py bump` 一次。`pyproject.toml` 是权威；脚本同步两个前端清单、两个安装器和 `uv.lock`，修正提交保留同一候选号。
4. 执行 `uv run --locked python scripts/release-version.py check --base 完整MAIN_SHA`，对新最终树完成相关聚焦验证、审查和全部适用 CI。
5. 紧邻合并再次读取 main 和 head；任一变化则返回刷新步骤。合并绑定核验过的 head，不强推、不绕过门槛。
6. 合并后核对远端 main、目标差异、版本和相关 push CI。任一失败先停止后续整合，在授权内诊断修复或请求回退决定。
7. 确认该更新正常，补齐 Issue/PR 证据并关闭问题后，再处理下一个候选。

版本是三段数字发布计数：PATCH 0–100、MINOR 0–10，按现有脚本进位；每次可发布 main 更新恰好前进一格，包括文档更新。多个并行候选暂时使用相同下一版本不赋予同时合并资格。

打 tag、发布安装器和部署是独立动作，须有相应授权。获准后使用现有 [Release installers](../../.github/workflows/release.yml) 流程和已审核 main 的精确数字 tag；不另建发布管线、不替换不匹配的历史 tag。仅合并成功不能称为已发布或已部署。

## 6. 背压、恢复和汇报

先稳定默认实现容量，再考虑增加并行。下列是人工复查的初始警戒线，不是已实现的自动限流，也不是硬件安全余量保证：

- 两个候选同时 CI 失败：暂停新增候选发布，优先诊断；不受影响且已授权的调查可继续。
- main 相关检查失败、版本不一致、数据完整性或科学正确性有疑点：停止后续合并。
- CI 排队明显超过通常耗时（初始提醒值 10 分钟）、可用内存低于 20% 或可用磁盘低于 15%：暂停新增重构建/下载并复查实际预算。大型任务即使高于比例也须满足其绝对资源要求。
- API 限流、网络或环境中断：按服务指示等待，保存证据并恢复原任务；不反复创建替代任务，不把失联当成成功。
- 根因重复、边界交叉或范围超出授权：重新分配所有权或拆分任务后继续。

连续维护按用户规定的期限和停止条件执行；「持续」不保证每秒执行，也不授权无限重试、制造改动或增加科学计算。恢复时先核对在途工作，停止请求到来后不再领取相应新任务，按要求安全收尾。

有成果、重要失败、风险变化或需要决定时汇报。汇总区分已证实问题、有效 PR、草稿/失败候选、合并且验证完成的改动，以及实际阻塞和下一步。观察返工、重复 CI、资源消耗和引入回归来改进流程，不以 PR 数排名。
