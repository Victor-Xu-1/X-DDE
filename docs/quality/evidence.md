# 证据与交接清单

[质量规范入口](README.md) · [维护流程](maintenance.md) · [前端验收](frontend.md)

用最短记录支持判断。小 Issue 保留下面 3–5 项，PR 选用不超过七个适用验收项；已有元数据和有效证据直接链接，勿重复抄写或重复验收。专项高风险材料可另附证据。受阻项写恢复条件，不勾选未执行的步骤；公开记录不含秘密或私有研究材料。

## Issue：五项简表

1. **问题与影响：** 已证实缺陷还是待调查现象，影响谁；已查重复 Issue/PR。
2. **复现与证据：** 版本/SHA、环境/输入、步骤、实际/预期结果；根因与假设分开。
3. **范围与负责人：** 唯一负责人、文件/接口/数据边界、直接消费者；分支和 base 可链接。
4. **完成条件：** 可判断的验收结果、必要检查、主要失败路径；资源/授权限制。
5. **跟进：** PR/CI 链接、阶段、最后核实时间、下一步和阻塞；验收后回填并关闭。

PR 使用 `Refs #编号` 普通引用；不使用合并时自动关闭问题的语法。

## PR：七项清单（按风险补充证据）

- [ ] **问题与定向回归：** 关联 Issue、根因/范围和消费者；同范围基线/修复后命令与结果，无法对照的限制。
- [ ] **边界检查：** 适用的失败、并发、数据/接口兼容、资源和回退证据；格式/差异/链接检查。
- [ ] **用户与科学验收：** 适用的真实浏览器/科学检查完成；无关项简述不适用原因。
- [ ] **独立审查：** 至少一名非作者、被审 head、结论和发现处置链接；阻塞清零。
- [ ] **精确 CI：** 完整 base/head、远端树核对、全部适用检查成功；没有必要检查缺失/取消/跳过。
- [ ] **串行整合：** 实时 main/head 与授权、一次版本递增、标准脚本检查；变化后刷新证据。
- [ ] **合并后确认：** main 改动/版本/相关 push CI 及受影响行为已确认，再回填并关闭 Issue。

前五项适用要求完成的候选可计为有效 PR；最后两项在轮到整合及合并后填写，不能提前勾选。草稿、运行中和受阻候选另列。整合负责人核对增量与新风险，不重复作者之外已有效完成的全文审查。

## CI 证据：一项检查一行

| 工作流 / 必要 job | 事件与模式 | 实际 SHA；PR 对应 base/head | run / attempt 链接 | 结论 |
| --- | --- | --- | --- | --- |
| 实际检查名 | push / pull_request / workflow_dispatch | 完整 SHA | 可审查链接 | 成功 / 失败 / 运行中 / 缺失 / 有理由的不适用 |

可以链接提供同等信息的查询结果。不要只写「checks green」。PR 合成提交与 head 分开记，版本/base/head 改变后按新候选核验；相同 SHA/树和范围的有效证据引用复用。

## 前端证据：一段摘要加实际画面

记录候选 SHA/构建身份、浏览器/版本/视口、受影响页面与消费者、数据身份（原生归档/模板/夹具/模拟接口）、操作及预期/实际结果、主要异常/恢复路径、截图和独立审查结论。

按变化补充：中英文、键盘/焦点、减少动态效果、动效目的和可打断性；性能问题记录同条件前后测量、重复次数、冷/热启动及目标。没有性能变化不强制全套性能报告。

全站评估时，从当前注册表核对模块/路由清单，记录页面/阶段、状态、操作、视口、数据来源、证据和负责人。小修复仅验证受影响子集并标明范围，不因存在全站清单就运行全部页面。

## 完成陈述

记录合并提交、时间、main CI 链接和实际结果。失败或验收未完成时，Issue 保持开放并停止后续整合。发布/部署另记实际 tag、包/安装身份和验收；未执行就不写「已发布」或「已上线」。
