# 工程质量与验收规范

[返回开发与发布](../development.md) · [仓库工程要求](../../AGENTS.md)

本目录把维护、界面体验、资源边界和证据门槛落实为可审查的工作清单。目标是可靠、清楚、可复现的研究软件；PR 数、测试数、视觉评分或「获奖级」描述都不能代替验收证据。

## 使用顺序

1. 阅读 [AGENTS.md](../../AGENTS.md) 和受影响模块的既有契约。
2. 按[持续维护流程](maintenance.md)先登记问题、明确唯一负责人和改动边界。
3. 按[验证分层与资源边界](validation.md)选择必要且有授权的验收范围。
4. 涉及页面、模块或交互时，使用[前端质量规范](frontend.md)。
5. 用[证据与交接清单](evidence.md)记录独立审查、精确提交 CI 和合并后结果。

这些规范补充现有要求，不覆盖或放宽它们。出现冲突时停止相关步骤，由维护负责人核对现行仓库规则、用户授权和实际实现；不得自行选择较宽松的一项。文档不授予发布、部署、额外科学计算或安全设置变更权限。

## 文件责任与更新

| 文件 | 维护责任 | 何时更新 |
| --- | --- | --- |
| `maintenance.md` | 维护负责人；独立审查人复核门槛 | 问题处理、协作、CI 或整合流程改变时 |
| `frontend.md` | 前端改动负责人；独立交互/视觉审查人复核 | 共享组件、页面清单、视觉或动效契约改变时 |
| `frontend-coverage.md` | 前端改动负责人；覆盖评估负责人核对注册表 | 入口/状态/共享消费者改变或开展覆盖评估时 |
| `validation.md` | 受影响模块负责人；科学相关内容由相应领域审查人复核 | 接口、结果含义、计算资源或科学验收要求改变时 |
| `evidence.md` | 整合负责人；独立审查人复核字段 | 证据、检查或交接方式改变时 |

具体人员在每个 Issue/PR 中指明；上表不是自动指派或新增仓库权限。作者不能独立批准自己的候选。维护负责人对规范之间的一致性负责，整合负责人对合并队列和发布编号的唯一性负责。

- 契约改变时，在同一 PR 更新对应规范、模块文档和验收项，说明原因与受影响流程；纯实现修复不必改规范凑数。
- 审查时以当前提交的注册表、工作流和版本脚本为准，不把旧文档中的模块/检查数量当作固定门槛。
- 定期维护复查及重要故障复盘时检查规范是否仍可执行；未解决的不一致登记为 Issue，不能以文档宣称实现已完成。
- 文档记录「必须检查什么」；只有仓库中实际存在且经过验证的代码、CI 或设置才能称为自动保障。原子任务认领、超时回收、分支保护或新增自动化须分别实现和审查。

## 保持现有产品边界

X-DDE 是面向早期药物发现的工作台及平台后端，统一管理任务、环境和研究资产。科学引擎保持独立，通过现有注册表、BackendRouter 和 Store/Worker 接入；不新增竞争性的任务队列或资产权威。平台可用、环境已安装、原生运行成功、科学结论可信是不同状态。

原始文件、历史版本、来源、单位、坐标和结果身份必须保留。界面打磨不能改写科学数据或制造计算结果；任务入口数量不代表每台机器均已具备执行条件。具体范围见[产品说明](../../README.md)、[前端布局契约](../frontend-layout.md)、[服务器验收](../server-acceptance.md)和[科学能力说明](../scientific-upgrade.md)。

面向药化/生物药研究人员，关键旅程是准备材料→审阅→一次提交→可信状态→结果交接；计算专家需要保留方法、参数、资源和原始产物的控制，维护者需要保护活动任务与升级数据。先消除错误执行、错误材料或无法恢复的阻塞，再打磨视觉细节；不另建产品路线或凭假设扩大能力。
